conversation

A design talk becomes decisions. Decisions become issues. Agents build, review and merge — and the docs remember. Every example in this talk is one real project, built this way from an empty repository in one afternoon.

01why a framework

Agents write code fast. Three other things break.

memory

Decisions vanish in chat

Two weeks later nobody knows why the money is an integer. The chat is gone; the code only shows what.

→ every decision is a row in the docs, with the rejected alternatives
scope

The agent builds its guess

An open question at prompt time becomes a silent assumption in the diff. Reviews then argue about the assumption, not the code.

→ the issue is the whole contract; thinking ends before building starts
trust

Who reviewed that?

Green CI is not a review. A PR needs evidence a person can read: suites, mutations, deviations, a verdict.

→ reviewer agents with a verdict line; a fix loop; a trail per issue
02the red line

Requisit: a B2B purchase-requisition and approval service.

Buyers draft, an approval rule matches, an approver decides with a reason, the order goes to the merchant. Many organisations on one instance; money that is never a float; an audit line on every state change.

why thisSmall enough to read in an afternoon, real enough to have authority, tenancy and money — the things that go wrong.
how farOne phase, two arcs. Arc 1 (the v1 flow) was built end to end by the framework; every artefact in this talk comes from it.

03the whole framework on one page

Three sessions, nine stages, one repository.

Each stage is a role with an input and an output. GitHub is the only shared state; no stage reads the chat of another. We zoom into each one.

stage 1rumble

Think and decide — with the model, before anyone builds.

whoA person and the model, in its own session. Web search on. No code.
inputEverything the person knows: a brief, ADRs, constraints, taste.
doesAsks back, researches, weighs options, writes rows: decisions (D), open questions with a reopening trigger (G), numbers to measure (M), a roadmap of arcs, a threat model.
outputDocs, reviewed like code — and issue drafts for the next arc.
ends with/task-out. The session never builds, never orchestrates.

stage 2task-out

The issue is the whole contract — written for an agent with zero context.

whoThe rumble session, as its last act.
doesCuts the arc into shippable splits of ~3k lines; pre-decides every choice an implementer would otherwise guess; declares dependencies.
shapeGoal · Context (the D-rows to honor, what NOT to do) · Acceptance criteria · Test expectations · Out of scope · Depends on · Suggested routing.
outputTask issues plus an umbrella with the run order in waves. The session ends here.
Requisit Arc 1: four issues, three waves, one umbrella — #2 · #3 · #4 + #5.
stage 3triage

The cheapest model stamps what the rest of the pipeline reads.

whoA small model in its own agent. Never implements.
doesChecks the issue is buildable, routes it: an area, a size, a risk. Dependencies open → blocked. Questions → needs-human.
outputLabels and one 🔎 comment. pipeline:build is the only "go".
size:L→ the architect runs first
size:S/M/L→ which model implements
risk:high→ a security review, and a person reviews after the fact

stage 4architect

Only for the big ones: a design inside the decided rows.

whensize:L, or the issue hands architecture choices to the implementer.
whoThe strongest model, read-only, web on.
doesModule layout, contracts, the test plan mapped to acceptance criteria with the mutation a reviewer should demand, new D-rows to write, a step plan for one PR — or a cut point.
outputA 🏛 Design comment on the issue. Never implements. A person can veto the D-rows before a line is written.
Requisit: 2 of 4 issues were size:L — both got a design; both PRs then overran the design's size estimate (M-009).

stage 5implement
One agent, one worktree, one draft PR with evidence.

  

    

      
whoThe project's implementer agent; model by size. Up to three at once, each in an isolated git worktree, in the background.

      
getsThe issue number, the branch, the verify command, "open a DRAFT PR, do not merge".

      
mustRun the board before the PR; try mutations and record what went red; write the D/G/M rows the issue named; list deviations from the design with reasons.

      
outputA draft PR whose body is the reviewers' starting evidence.

stage 6review
Two lenses, one verdict line — readable by someone who was not there.

  

    

      
whoA quality reviewer always; a security reviewer on risk:high. Own worktrees, read-only.

      
doesReuses the PR's evidence: the suites it names plus at most two mutations of its own. Verifies every finding before writing it.

      
outputOne comment, findings grouped 🔴 must-fix / 🟡 nit, ending in VERDICT:.

      
neverLabels needs-human for a red — a red goes to the fix loop.

stage 7fix loop
At most two rounds. Then a person.

  

    

      
whoThe same implementer, on the same branch, with the findings verbatim.

      
doesFixes every red, the nits where cheap, replies with a reason otherwise; pushes; one comment mapping each finding to a commit or a reason.

      
thenRe-review by the one reviewer that held the red — new reds only. A second re-review only if the fix touched auth, transport or policy.

      
stopA red after round two → needs-human. The orchestrator counts the rounds.

stage 8gate & trail
Merge, prove main is green, write down what it cost.

  

    

      
whoThe orchestrator session — it never reads code; it merges, verifies and writes.

      
doesMerges main into the branch itself (resolve → verify → commit, never one chained command); fixes one-liner nits; ready → squash-merge; the full board on main after every merge.

      
thenAssigns risk:medium|high PRs to a person for review after the fact; unblocks dependants; posts the 📋 trail; ticks the umbrella.

      
outputThe trail: stages × model × outcome × tokens — the cost ledger the next rumble reads.

stage 9the docs
The memory — and a check that keeps it honest.

  

    

      
whatDecisions (append-only, addenda when a PR meets reality) · gaps with triggers · measurements that read "pending" until measured · a research log with sources.

      
ruleA task that changes what a doc describes updates the doc in the same branch. A reference without a row is a red finding.

      
checkcheck-anchors and render --check run in the board: dangling D/G/M references or a hand-edited generated file fail it.

      
loopThe next rumble starts by reading these — not the chat.

07several people
The issue is the contract, so the author does not matter.

  

    
rumble
Everyone rumbles. Rows and issues come as a PR and are reviewed like code. Reserved numbers avoid collisions.

    
orchestrate
One person per arc runs the pipeline. State is on GitHub, so the next wave can be taken over in a new session by someone else.

    
review
Verdicts, evidence and trails are written for a person who was not there. Disagree in a review comment — the fix loop treats it like a finding.

    
merge
gate.merge: human and the gate stops at "ready for review". CODEOWNERS per area decide who the inbox is.

  







  
08where this fits
Agent features are decisions plus contracts plus reviewed PRs.

  

    
buyer · merchant agents
What an agent may do is a D-row and a risk label before it is code. Requisit's drafting agent never approves — decided in the rumble, enforced in review.

    
pwa · commerce core
One framework repo, one framework.json per codebase: its own areas, implementers, verify board and risk:high list.

    
both runtimes
Claude Code and Codex from the same source; the model per stage is a binding, not a habit.
